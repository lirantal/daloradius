# UNIT-035 — Realms et proxies PDO avec publication du fichier

Les six pages de création, édition et suppression des *realms* et *proxies* utilisent PDO pour leurs mutations et leurs lectures de formulaire. Le générateur `saveRealmsProxys.php` relit les deux tables sur le **même PDO transactionnel** que la mutation ; les noms des tables configurées sont validés, les valeurs SQL sont liées et les deux tables doivent être InnoDB. Un verrou consultatif propre à la base sérialise les écritures coopérantes et la génération. Les suppressions multiples valident tous les noms avant la première suppression ; une erreur tardive annule tout le lot. La création conserve l'identifiant PDO réel plutôt que de le rechercher dans une table de factures sans rapport.

Le fichier configuré doit exister, être un fichier ordinaire signé `# daloradius`, lisible et modifiable avec un répertoire inscriptible. **Un fichier administrateur non signé ou un lien symbolique n'est pas écrasé** : contrairement au chemin PEAR, aucun backup contenant potentiellement des secrets n'est conservé. Le nouveau contenu est écrit dans le même répertoire dans un fichier temporaire mode 0600, synchronisé, puis publié par renommage atomique en conservant les permissions et la propriété du fichier précédent. Le commit DB suit le renommage ; une erreur avant le commit provoque un rollback SQL et tente de restaurer atomiquement l'ancien fichier, sans laisser de copie temporaire. Une erreur de commit, de rollback ou de restauration dont l'issue ne peut être établie affiche un **état incertain** et demande la vérification du fichier et de la base avant une nouvelle opération. Un fichier et une transaction SQL ne constituent pas une transaction atomique commune : la fenêtre entre renommage et commit, un processus externe ne prenant pas le verrou, et un crash machine restent des risques résiduels. Le service FreeRADIUS n'est pas redémarré automatiquement.

Corrections ciblées par rapport au chemin PEAR : le nom du proxy est réellement renommé lors d'une édition (l'ancien UPDATE cherchait la *nouvelle* valeur dans `WHERE` sans changer le nom), `%` n'est plus supprimé, le formulaire distingue `type` et `nostrip`, et une valeur littérale `0` de secret est écrite dans le fichier. Les contrôles d'ACL, le menu et certains sélecteurs partagés restent sur PEAR ; ces lectures ne participent pas à la transaction PDO.

Validation : `REALM_PROXY_BASELINE=1 PYTHONDONTWRITEBYTECODE=1 python3 tests/realm_proxy_http.py`, puis sans `REALM_PROXY_BASELINE`, avec HTTP/PHP/MariaDB et fichier jetables. Parcours communs des six pages : création, édition, suppression, état SQL et contenu généré. Candidat : refus de CSRF invalide sur les six pages, échecs SQL réels en création et édition de chaque famille, échec SQL sur une suppression tardive de chaque famille, nom périmé, refus d'un fichier absent, non signé ou symbolique et de MyISAM, contention du verrou, valeurs malformées, restauration après publication et avertissement d'une issue de commit ambiguë. Le scénario de lien symbolique vérifie que le lien et les octets du fichier ciblé restent inchangés. Les deux dernières erreurs sont **injectées dans la seule copie jetable du helper**, pas produites par une vraie panne de MariaDB. Le test compare les secrets à l'intérieur de SQL, les exclut des snapshots et vérifie qu'ils ne figurent pas dans les logs. Aucune validation d'une configuration FreeRADIUS chargée par un démon ni aucun essai en production. **Aucune clé, aucun mot de passe, jeton, secret ou identifiant de connexion ne doit être conservé.**
