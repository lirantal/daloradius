# UNIT-028 — Authentification primaire des opérateurs

`app/operators/dologin.php` utilise PDO pour la lecture de l'identité, la mise à jour conditionnelle du hash local, l'association conditionnelle de l'identité LDAP et l'écriture de `lastlogin`. Seule la table des opérateurs configurée est acceptée comme identifiant SQL ; les valeurs sont liées. La table doit être InnoDB.

Après vérification du mot de passe ou de l'annuaire, une nouvelle lecture verrouillée contrôle l'ID, le nom, le fournisseur et le hash local ou l'identifiant LDAP avant de créer la session. La mise à jour `lastlogin` est vérifiée et commitée avant l'ouverture de la session ; pour MFA, elle reste gérée lors de la validation OTP. La localisation sélectionnée n'est conservée dans la session qu'après réussite de l'authentification primaire, mais détermine la connexion sur laquelle les identifiants sont vérifiés. Une mise à jour concurrente du mot de passe ne peut être écrasée par le rehash : son `UPDATE` compare l'ancien hash et refuse la connexion si la comparaison échoue. L'association LDAP accepte une association concurrente à la même identité et refuse une identité différente.

Hors périmètre : `login-otp.php` et ses écritures PEAR, ainsi que les lectures partagées d'ACL. Le rehash local est une opération CAS distincte de la transaction de validation finale : un échec ultérieur peut laisser le hash renforcé, sans ouvrir de session. Les sessions déjà ouvertes avant une révocation restent soumises aux contrôles existants.

Validation : `OPERATOR_LOGIN_BASELINE=1 python3 tests/operator_login_http.py` et `python3 tests/operator_login_http.py` sur HTTP/PHP/MariaDB jetables, plus le test PHP `operator-auth-login.test.php` et les régressions ciblées création/édition/suppression d'opérateurs. Les parcours normaux sont comparés à PEAR ; les cas PDO couvrent également les entrées malformées, la concurrence sur l'association LDAP, la réinitialisation concurrente pendant le rehash et un échec injecté sur `lastlogin` (aucune session ouverte). Les données factices sont générées à l'exécution ; aucune clé, aucun mot de passe, jeton, secret ou identifiant de connexion ne doit être conservé. Il ne s'agit ni d'un déploiement ni d'une validation en production. L'authentification auprès d'un véritable annuaire LDAP n'est pas couverte ici.
